      How checking and saved progress work
      • Checks compare the requested columns and row values, not exact SQL text. Aliases and equivalent query forms are accepted. Column order must follow the displayed contract. Duplicates are counted; row order matters only when the task requests a sort. These aggregate tasks do not require sorting. Grouped results may appear in any row order.
      • Each task has three checks: the base database plus two visible validation datasets. Extra sales test repeated products and prices, zero quantity/price, fractional averages, new groups, and correct foreign-key joins. Relational validation also includes unsold catalog products and a region without sales. You can inspect every dataset using the selector above the task list. The base dataset stays unchanged.
      • Small numeric differences are tolerated, but do not round averages or replace numeric results with formatted text. Text and NULL values are compared as values. SQLite LIKE is case-insensitive for ordinary ASCII letters. Expected answers are visible after checks and in the page source; this is a practice tool, not a secure examination system.
      • When all three checks pass, the exact successful query and completion status are saved separately from drafts. On a later visit, completed tasks restore their successful query. Use Restore latest draft for a later unfinished attempt. Progress is local to this browser/profile and computer; clearing site/browser data removes it. Return using the same site address. Private browsing or unavailable storage can prevent persistence.
      • Every run uses a fresh read-only copy of the selected dataset. SQL errors or failed attempts cannot damage the supplied databases. Stop terminates the worker; a query is also stopped after five seconds. Results are limited to 1,000 rows. The library reloads after stopping.
      Source notes and SQL engine

      All seven questions from each supplied HL Word document are included. The flat-file data reproduces all 15 sales from the table in “SQL Aggregate Functions Write Code FlatFile DB.docx”. The relational document contains the questions and a link to relational_sales_dataset.sql, but no embedded database. This page therefore uses a teaching reconstruction, not a copy of that missing script. The reconstructed schema and its data can be inspected and downloaded above.

      Revenue means SUM(quantity × unit price). The flat-file Tech average uses matching sale records; the relational Tech average uses each product in Products once, including unsold products. Regional averages use unit prices per sale record, with repeated sales counted separately and regions without sales omitted. These conventions make the short task wording precise. No task asks for a quantity-weighted average. The base datasets describe the same transactions; validation datasets add labelled teaching records.

      The page uses sql.js 1.14.2, which runs SQLite using WebAssembly. JavaScript, CSS, task definitions, source data and the worker are embedded in this page. The SQL engine loads from jsDelivr and requires internet access when loading; offline availability is not guaranteed. No query or database is uploaded by this page. The table preview is embedded too, so it is available before the SQL engine loads. These tasks use SQLite syntax, which differs in some details from MySQL, PostgreSQL or Access.
