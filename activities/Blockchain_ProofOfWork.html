Digital currency · Blockchain · Proof of work

Build a block. Find its proof.

Create one transaction per block, watch the system test whole-number nonces, then append a successful block to the chain. The genesis block is already present.

Teaching model: MD5 and a four-bit target make the process easy to watch. A timestamp is part of the data being hashed; it cannot be read out of the hash. Proof of work makes rewriting history costly, rather than impossible.

1. New transaction

Choose the recorded event time in your local time zone. The block stores its UTC equivalent. The timestamp stays fixed while the nonce is tried.

The previous block’s hash is added automatically. This demo does not model balances, digital signatures or real payments.

Optional experiment: change an earlier transaction
First add at least two transaction blocks. Change an amount below to recalculate that block’s hash using its existing nonce. Later blocks still hold their old links. Inspect what fails, then try re-mining the affected history.
Re-mining works block by block in the proof-of-work panel above. Accept each repaired block to continue. Even if the local chain passes all checks again, the accepted reference copy has not been rewritten. A real network would also apply its consensus rules.


1. A fixed block input
The sender, receiver, datetime, amount and previous hash stay fixed during mining. The whole-number nonce is the value being varied.
2. Trial and check
Compute MD5 for each nonce and inspect its final four bits. Stop when they are 0000. There is no known shortcut from the target to the required nonce in this demonstration.
3. Link the next block
After acceptance, the block’s hash becomes the previous-hash value of the next block. Changing earlier data therefore affects later links.


Teaching notes and what this model simplifies
The timestamp: datetime is a recorded field. It participates in the hash calculation, but is not a date hidden inside the digest. In this demo it is chosen by the user, not independently verified.
The nonce: proof of work is the work of trying and checking candidate values. The stored field called proof-of-work here is the successful nonce, a non-negative whole number. A valid nonce might be 0. Sometimes the first attempt succeeds; there is no guaranteed delay or fixed number of attempts.
The target: MD5 has 128 output bits, displayed as 32 hexadecimal digits. Each hexadecimal digit represents four bits. Ending in hexadecimal 0 therefore means ending in binary 0000. Under an approximately uniform distribution, this very small target succeeds roughly once per 16 independent attempts on average, not exactly every 16 tries.
Hashes and security: a hash acts as a fingerprint but is not guaranteed to be unique. MD5 has known collision weaknesses and is used here only as the requested teaching model. Real systems use stronger constructions and much more demanding work targets. The artificial animation delay makes trials visible; it is not a property of MD5 or a realistic mining speed.
Why tampering is costly: changing a block changes its hash. Updating its successor’s previous-hash value also changes that successor’s hash and usually invalidates its nonce. Work must be repeated along the affected chain. Our tiny four-bit toy target is deliberately easy to re-mine. Proof of work does not make attacks mathematically impossible; network agreement and the relative work of honest participants and attackers matter.
A local demonstration: one transaction per block, a pre-mined fictional genesis block and a separate accepted reference copy are used for clarity. Real blocks can hold many transactions. No real currency, wallet, account validation or distributed consensus is implemented.
References: Bitcoin’s proof-of-work and chained-block model; MD5 security considerations (RFC 6151).
